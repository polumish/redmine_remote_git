# Updater — консолідована сторінка апдейтів парку систем (ідея)

> Статус: **ідея / чернетка для обговорення**, ще не реалізовано. Цей документ фіксує
> задум, щоб не загубити його, і дає початкову точку для проєктування, якщо рішення
> буде рухатись далі.

## Проблема

Апдейти інфраструктури зараз розкидані по різних місцях і форматах:

- оновлення ОС на серверах (apt/dnf security patches, kernel);
- оновлення Docker-образів і самих контейнерів;
- оновлення застосунків: WordPress (core/плагіни/теми), Redmine (core/плагіни),
  та інших сервісів;
- оновлення баз даних (MySQL/PostgreSQL мінорні й мажорні версії, розширення).

Немає єдиного місця, де видно: що застаріло, наскільки критично, коли востаннє
оновлювались, і хто/коли планує наступний апгрейд. Рішення про апгрейд і його
виконання — ручні, не пов'язані між собою процеси.

## Ідея

Нова сторінка/модуль **Updater** (можливо — top-menu пункт за аналогією з наявним
**Git**-оглядом у цьому плагіні) для "парку" (fleet) хостів/сервісів, яка:

1. **Збирає стан апдейтів** по всіх об'єктах парку в одному реєстрі:
   - хост/сервер → доступні security/OS-апдейти;
   - Docker-контейнер/сервіс → поточний тег образу vs. новіший доступний;
   - застосунок (WordPress, Redmine, інші) → поточна версія core/плагінів/тем
     vs. остання відома;
   - база даних → поточна версія vs. підтримувана/остання.
2. **Дозволяє планувати** апгрейди: призначити виконавця, дедлайн/вікно
   обслуговування, пов'язати з Redmine issue/задачею (природний зв'язок,
   оскільки це Redmine-плагін), відмітити залежності (спочатку БД, потім
   застосунок, наприклад).
3. **Дозволяє проводити** апгрейд і фіксувати результат: статус (заплановано /
   у процесі / виконано / відкладено / провалено), нотатки, посилання на лог.
4. **Інтегрується із зовнішніми системами моніторингу** для збагачення даних і
   контексту, а не для дублювання їхнього функціоналу:
   - **Zabbix** — стан хостів/сервісів, наявні тригери/аларми, які можуть
     впливати на вікно обслуговування;
   - **Uptime Kuma** — поточна доступність сервісу перед/після апгрейду;
   - **Wazuh** — security-алерти/вразливості (CVE), які можуть підвищувати
     пріоритетність конкретного апдейту.

## Standalone vs. Redmine-плагін — вирішено

Ідея спочатку не задумувалась як прив'язана до Redmine — це загальна ідея
сторінки/сервісу для парку. **Рішення: реалізовувати як окремий Redmine-плагін**
(робоча назва `redmine_updater`), а не як standalone-сервіс. Причина —
природний зв'язок апдейту ↔ issue/проєкт і перевикористання Redmine
auth/permissions/UI-теми та деплою, той самий, що й у решти Redmine-екосистеми
в цій команді.

Це окремий плагін від `redmine_remote_git` (інша предметна область — fleet/ops,
а не git-репозиторії), з опційними посиланнями між ними (issue ↔ репозиторій ↔
апдейт).

## Відкриті питання (потребують рішення перед проєктуванням)

- **Джерело даних про версії**: агент на хостах, push зі скриптів CI/CD, чи
  periodic pull через SSH/API з кожного джерела (Zabbix API, Docker registry
  API, WP-CLI, `apt list --upgradable`, тощо)?
- **Формат об'єкта "парк"**: чи це нові Redmine-моделі (хости, сервіси,
  компоненти) в межах цього плагіна, чи окремий плагін/сервіс, який лише
  публікує дані в Redmine через issues/custom fields?
- **Модель безпеки**: які креденшали потрібні для читання версій із хостів/
  контейнерів/БД, і як їх зберігати (аналогічно шифруванню токенів у цьому
  плагіні — AES-256-GCM, write-only API)?
- **Частота опитування зовнішніх API** (Zabbix/Uptime Kuma/Wazuh) і межі
  навантаження на них.
- **UI**: окрема top-menu сторінка з фільтрами/сортуванням (за аналогією з
  Git overview: `app/views/.../overview`), чи dashboard-віджет для проєкту.

## Можливий грубий план ітерацій (якщо рішення — робити)

1. Реєстр об'єктів парку + ручне введення поточної/бажаної версії (без
   інтеграцій) — MVP для видимості проблеми.
2. Планування апгрейду: статус, виконавець, дедлайн, зв'язок з issue.
3. Одна зовнішня інтеграція (найімовірніше Zabbix, як найбагатше джерело
   інвентарю хостів) для автозаповнення реєстру.
4. Uptime Kuma — перевірка доступності до/після апгрейду.
5. Wazuh — пріоритизація за CVE/security-алертами.

## Не входить у цей документ

Конкретна схема БД, API-контракти та код — свідомо не описані: рішення про
архітектуру (окремий плагін vs. розширення) має бути прийняте до того, як
писати специфікацію реалізації.
